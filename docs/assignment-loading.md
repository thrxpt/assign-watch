# Assignment loading failures

An unsuccessful request does not establish that a class has no assignments. Both the to-do list and calendar show loading failures for visible classes. The congratulatory empty state is reserved for a list with no visible assignments, pending classes, or failed classes. Hidden classes do not surface loading errors.

The dialog requests assignments for all enrolled classes in one batch and exposes results per class. If the batch request fails for a reason other than HTTP 429, retry each class separately so successful classes remain usable when another class fails.

The calendar uses a compact warning above the grid so the error does not compete with the calendar for space. The retry action sits alongside the warning on wider screens and below it on narrow screens.

When LEB2 responds with HTTP 429, display a localized request-limit message asking the student to wait before trying again. If the response has a valid `Retry-After` header, show its remaining wait in the **Try again** button and keep the button disabled until the wait expires. Do not automatically retry that query, including when the dialog is reopened. If the shared batch request is rate limited, **Try again** retries that request once for all enrolled classes; if a per-class fallback is rate limited, it retries only failed visible classes. The action is disabled while a retry is in progress. Other failures receive a general loading-error message and retain the existing three automatic retries.

Keep assignments already loaded in the current page session visible after a failed refresh, with a warning that they may be outdated. Successful classes remain usable when other classes fail.

After a full-page LEB2 navigation, the dialog can restore cached assignments when it opens. Use the snapshot only when its non-null student ID exactly matches the current nonempty student ID; legacy snapshots without an owner are not trusted for display. Restore only nonempty rows for currently enrolled classes, and leave classes missing from the snapshot unseeded so their live query can determine whether they are empty. Read the snapshot before enabling queries for that student. Treat restored rows as stale, show the warning while they refresh, keep both rows and warning after a failure, and clear the warning after that class refreshes successfully. Preserve existing query data (including successful empty results), errors, and active requests. Same-page query results keep the existing five-minute freshness window.

## Class roster ownership

The background worker saves the latest observed student and their enrollment together with a durable generation. The dialog queries only a confirmed worker-approved roster owned by the student the page identifies. A missing, unresolved, or mismatched roster is **unknown** enrollment. Both views prompt the student to sync from `/class`. A confirmed roster with zero classes shows "all caught up" in both views. The worker can approve a pre-upgrade roster when it observes the same student that owns it.

On `/class`, a resolved scrape requires at least one student card, each with a valid class ID, title, and description read within the card or an unambiguous card wrapper. TA cards are skipped. The page checks the student again before it sends the scrape. Unfinished or malformed markup, a page with no student cards, and a student change on an already observed page publish only the student. The worker retains confirmed enrollment for a repeated observation of that student and starts with unresolved enrollment when the student changes. Confirming an empty roster from LEB2 still requires a reliable empty-state marker.

The generation changes when the owner or class membership changes. A successful class response enters the raw cache before the dialog exposes it to the manual-date editor. The worker accepts a response only if its owner, generation, and class still match the saved enrollment. The dialog drops superseded work without automatic retries and starts eligible requests under the new generation. Completed results for the same student, including successful empty results, retain the page-session freshness window. Failed HTTP 429 queries remain manual-only.

When confirmed enrollment changes, the worker prunes removed classes from the same student's snapshot even if all subsequent fetches fail. Offline reminders use the confirmed roster to exclude removed classes while a failed prune awaits repair. A failed prune for another student can be deferred while publishing a new owner. The worker saves the excluded class IDs with the new scope and repairs the snapshot before publishing a roster that could expose those rows again. Until the first worker-approved scope is saved, the previous last-student ID still gates owned offline reminders. Legacy unowned snapshots remain eligible for LEB2 reminders.
